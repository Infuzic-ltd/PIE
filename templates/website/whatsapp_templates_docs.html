WhatsApp Business API — Template Submission Plan

PIE Real Estate needs 14 message templates

Four cover inventory changes, three cover the lead pipeline, five (one per property count) cover property recommendations to clients, one covers client milestones and one covers affiliate onboarding with login details. Every template follows WhatsApp’s variable rules (see Template rules), so none will be rejected for a variable at the start or end.

Scope → grouped by shape Lead-facing templates → Utility Language → English only Tier 3 (needs new fields) → skipped

At a glance

All fourteen submit under Meta’s current three-category system (Utility / Marketing / Authentication) and every one here is Utility. The inventory and internal templates report on an operational change the recipient already manages; the two client-facing templates are scoped to a reply to that specific lead’s own inquiry or an update on their own active deal (see the compliance notes in those cards).

Template rules (read before submitting)

Meta rejects templates, or individual sends, that break these rules. The error “variables can’t be at the start or end of the template” is rule 1. Every template on this page already follows all of them.

#RuleWrongRight
1The body can’t start or end with a variable{{1}} has been assigned.Hello {{1}}, … open it in the CRM.
2Two variables can’t sit next to each other with only spaces or line breaks between them{{1}} {{2}}📋 Regarding: {{1}} 💰 Figures: {{2}}
3A variable’s value can’t contain line breaks, tabs or more than 4 spaces in a row. Lists need one variable per line.{{2}} = "1. Flat 2. House"Option 1: {{2}} Option 2: {{3}}
4Every variable must be filled on every send. Values can’t be empty.One template for “up to 5” itemsOne template per item count
5Enough fixed text around the variables. Too many variables for the length gets rejected.{{1}} {{2}} {{3}}Labels on every line
6A URL button’s variable can only go at the end of the link. At most 2 URL buttons.https://site.com/{{1}}/viewhttps://site.com/crm/{{1}}
7Limits: header 60 characters, body 1,024, footer 60. Footer has no variables.——
8Give a sample value for every variable when submitting—Use the “Sample value” column

Inventory alerts — agents & affiliates

All four share one shape: a header naming the property, a body carrying only what changed (previous value → new value) plus a timestamp, and an optional button back into the CRM. Status labels are passed in as plain text, not hard-coded in the template, so new statuses (e.g. adding “On Hold” or “Withdrawn” to the Property model — see Implementation notes) don’t require a template resubmission.

Client-facing updates — leads & customers

Written for a phone screen: short lines, one idea per line, and a link on its own line so it’s easy to tap. The recipient has no CRM login, so links go to the public website.

property_recommendation_1 … _5
Covers: 1 to 5 matching properties sent to a client, each with a link to its page on the website
UtilityEnglish (US)

WhatsApp requires every variable to be filled on every send, and a value can’t contain line breaks. So one template can’t hold “up to 5” properties. Submit five templates with identical wording: property_recommendation_1 to _5, where the number is how many properties it holds. The sending code picks the one that matches the number of recommendations. The spec below is property_recommendation_5. The others simply stop after Option 1, 2, 3 or 4.

Implementation notes

Not part of the Meta submission, but worth flagging before build:

The Property model’s STATUS_CHOICES currently only has Active / Inactive / Sold — “On Hold” and “Withdrawn” aren’t stored states yet. The templates above take status as free text, so no resubmission is needed once those states are added, but the status-change logic itself still needs to be built.
Price history isn’t currently tracked (only narrative activity-log text) — capturing the previous price at the moment of change will need a small model change to populate property_price_change accurately.
Lead.follow_up_date and Lead.visit_scheduled_at are stored today but nothing reads them back — the reminder and visit-reminder triggers in lead_reminder_alert need a new scheduled job (daily for follow-ups, hourly or T-1-day for visits), not just a hook on an existing view. Agent Target Pace needs a similar new weekly job.
LeadPayment creation (lead_add_payment) and locking deal financials (lead_set_deal_financials) currently call zero notification code at all — wiring WhatsApp here means adding the first-ever notification hook to both views, in-app included.
Swap your-pie-domain.com in every button URL for the CRM’s real production domain before submitting. Each WhatsApp template is also sent one recipient at a time via the Cloud API — fanning a single event out to every relevant agent/affiliate/lead is orchestration this document doesn’t cover.
Skipped on purpose: document-expiry reminders (PropertyDocument has no expiry/valid-until field today) and affiliate commission-earned alerts (no commission field exists anywhere on the affiliate relationship). Add the underlying field to the data model first, then template these.
Affiliate approval (affiliate_set_status) needs to generate a temporary password, call set_password and send it in affiliate_approved_alert. The invite password can’t be reused because only its hash is stored.
Property recommendations: build each summary line (60 characters or fewer, no line breaks) and pick property_recommendation_N where N is the number of properties (1–5). The existing wa.me share text is multi-line, so it can’t be reused as a variable value.
